# 恢复执行接入异步任务队列

## Context（背景与目标）

当前 `POST /instances/{id}/backups/runs/{runID}/restore` 在 HTTP 请求内由 [backups.go](file:///Users/applepig/项目/字节/swe/34-autobrr--qui/tasks/T002-qui/T002-qui-workspace/internal/api/handlers/backups.go) 的 `ExecuteRestore` 同步调用 `Service.ExecuteRestore`（[restore_execute.go](file:///Users/applepig/项目/字节/swe/34-autobrr--qui/tasks/T002-qui/T002-qui-workspace/internal/backups/restore_execute.go)），直接做分类/标签/torrent 的增改删。问题：

- 长恢复会被请求超时打断；重复点击会并发改同一个 qBittorrent 实例（无实例级互斥）。
- 没有独立 run 状态、进度、取消入口。
- 进程退出后 in-flight 恢复无任何恢复入口。

目标：把恢复执行迁移到持久化异步队列。每次恢复创建唯一 run 记录（快照 run id、实例、模式、状态、起止时间、错误、进度、操作日志、取消请求）；实例级互斥（重复请求复用同一 run 或明确 busy）；后台串行执行 `PlanRestoreDiff` + 执行；客户端可查进度/取消（取消只发生在操作间安全边界）；启动时把 queued/running 标记为 interrupted，未执行/失败操作可重放、已执行不重复，损坏 run 跳过并报告；incremental/overwrite/complete 三模式同队列，dry-run 只生成计划；关闭服务时当前 run 到安全边界、排队 run 取消。

### 已确认决策
- **全局单 restore worker**：所有实例的恢复串行执行；另用 per-instance in-flight map 提供互斥与 busy/复用语义。
- **重放策略**：resume 时对当前实况重新跑 `PlanRestoreDiff`，结合操作日志——已 succeeded 的操作跳过（绝不重复），pending/failed 重放，新计划里已不需要的旧 pending 标记 skipped。
- **前端做完整 UI**：进度、取消、busy/复用、interrupted 一键恢复、操作日志。

## 3. 恢复队列与生命周期

接线（避免改动 NewService 约 20 个测试调用点）：给 `BackupStore` 加 `Querier() dbinterface.Querier`，在 `NewService` 内当 store 非 nil 时构造 `models.NewRestoreStore(...)`，并始终初始化 channel/maps；worker 仅在 `Start()` 启动。[main.go](file:///Users/applepig/项目/字节/swe/34-autobrr--qui/tasks/T002-qui/T002-qui-workspace/cmd/qui/main.go#L787-L791) 无需额外构造（store 已传入）。

- `ErrRestoreInstanceBusy`；`RestoreRequest{InstanceID, BackupRunID, Mode, Options RestoreOptions, RequestedBy}`。
- `QueueRestoreRun(ctx,req) (run, reused, err)`：先用现有 `store.GetRun` 校验快照 run 归属；in-flight 锁内查该实例 queued/running：**去重键一致**（backupRunId/mode/dryRun/3 个 bool/排序后 excludeHashes）→ 返回已有 run（reused=true）；不一致 → `ErrRestoreInstanceBusy`；否则插 queued、占 inflight、投递 channel（沿用 `QueueRun` 的 `select ctx.Done()` 写法；入队失败标 interrupted，不删行——账本有保留价值）。
- 单个 `restoreWorker(ctx)`（`Start()` 中加入现有 `s.wg`）；`handleRestoreJob`：注册 per-run `context.WithCancel`，`cancel_requested=1` 直接收尾 canceled，否则 `queued→running`。
  - dryRun：`PlanRestoreDiff` → `ReplacePlan`（零 ops）→ `SaveResult(success)`，不做任何变更。
  - 真实执行：重新 plan → `expandRestoreOps(plan)` 展开为原子操作 → `ReplacePlan` → 读 `OpStateMap` → 跑账本驱动执行器。终态：`ctx.Err()`→canceled；计划/基础设施致命错误→failed；有任意 op failed→**failed**（result_json 含 applied 与 errors，可 resume 重试）；否则 success。每条终态路径都清理 inflight/cancels/progress，并 `emitRestoreRunActivity`。
- `CancelRestoreRun(id)`：置 `cancel_requested`；queued 由 worker 不执行直接收尾，running 调注册的 cancel func（仅循环顶/操作间生效）。
- `GetRestoreRunProgress(id)`（内存 map，DB 列兜底）、`ListRestoreRuns/GetRestoreRun/ListRestoreOps` 透传。
- `ResumeRestoreRun(id)`：仅允许 interrupted/failed/canceled；清 cancel_requested/error/时间戳 → queued → inflight 检查 → 入队；账本保留，worker 重新 plan 并跳过 succeeded。
- 启动恢复 `recoverInterruptedRestoreRuns(ctx)`，在 `Start()` 内紧邻 `recoverIncompleteRuns`：`FindActiveRuns`；**损坏判定**：快照 run 已不存在（sql.ErrNoRows）或 options_json/非空 plan_json 无法解析 → 置 failed 并写错误 + `log.Warn`；其余 → interrupted；逐条发 activity。
- `Stop()`：先 `CancelAllQueued()`（排队→canceled），再现有 `s.cancel()`，让当前 run 在下一个安全边界停下并标 canceled，`s.wg.Wait()` 等 worker 退出。恢复只读缓存 blob、不落临时文件，无需额外临时清理。
- [activity.go](file:///Users/applepig/项目/字节/swe/34-autobrr--qui/tasks/T002-qui/T002-qui-workspace/internal/services/activity/activity.go) 新增 `KindRestoreRun Kind = "restore.run"`，加 `emitRestoreRunActivity`。

## 风险/边界

- re-plan 漂移：新计划不再需要的旧 pending 置 skipped，不执行。
- add 歧义（qB 已接受但响应丢失）：resume 再 add 可能被 qB 拒，记 failed 并透传 qB 信息，交人工处理。
- 批量部分应用维持既有 best-effort 语义；inflight/cancels 必须在所有终态路径（含 plan 失败）清理。
- `ResumeWhenComplete` 无 ctx，保持边界后 best-effort。
- PG：无 `LIMIT -1`、IN 分块、upsert conflict target 与唯一索引一致、BIGINT 扫 int64。
- 大量 torrent：进度写节流 + ops 一次性批量 upsert，避免每操作事务。
